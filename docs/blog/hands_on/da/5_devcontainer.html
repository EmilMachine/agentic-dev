5. Kør Claude Code i en sandbox

Claude Code kan læse filer, skrive kode og køre shell-kommandoer. Det er dens styrke - og dens risiko. Hvis den laver en fejl eller gør noget uventet, vil du helst have at det sker inde i en container og ikke på din maskine.

En devcontainer kører dine værktøjer (Python, uv, Claude Code) inde i Docker. Din kode bor stadig på hosten og er monteret ind i containeren. Hvis containermiljøet går i stykker, docker rm -f og genbyg.

Hvad er og ikke er beskyttet

Det er vigtigt at være ærlig her - en devcontainer er ikke en fuld sandbox for dine filer.

Følgende er bind-monteret fra din host, hvilket betyder at ændringer (og sletninger) inde i containeren påvirker de rigtige filer:

Sti inde i container Host-sti
workspace-mappe din projektmappe
~/.claude.json ~/.claude.json
~/.claude/ ~/.claude/
~/.cache/uv ~/.cache/uv

En løbsk rm -rf ~ inde i containeren ville slette disse på din host. Git er dit sikkerhedsnet for kode - commit ofte.

Bemærk om ~/.claude i særdeleshed: vi monterer den, så Claude Code allerede er logget ind og har dine skills og konfiguration tilgængeligt inde i containeren. Afvejningen er, at et kompromitteret eller ondsindet projekt kunne korruptere din Claude-konfiguration - og den korruption ville vedvare på tværs af alle andre projekter du åbner, da de alle deler den samme ~/.claude fra hosten. Det er en kendt risiko. Se hærdningsmuligheder til sidst.

Hvad er isoleret:

  • Værktøjsmiljø. Dårlige pip install, npm install -g- eller apt-installationer forbliver inde i containeren og forurener ikke din host.
  • Processer. Løbske processer, portkonflikter og baggrundsdæmoner er begrænset til containeren.
  • Rent udgangspunkt på forespørgsel. Ødelagt miljø? docker rm -f og genbyg - din kode og dine legitimationsoplysninger er urørte, da de bor på hosten.
  • Reproducerbart miljø. Kolleger får de samme værktøjer uden "virker på min maskine".

Den primære beskyttelse er miljøisolation, ikke filisolation.

Forudsætninger

  • Docker installeret og kørende
  • devcontainer-cli (fastlåst version for at beskytte mod supply-chain-angreb):
npm -g install @devcontainers/cli@0.87.0

Tilføj til ~/.bashrc eller ~/.zshrc:

export PATH="$HOME/node_modules/.bin:$PATH"

Kør source ~/.bashrc (eller ~/.zshrc) eller åbn en ny terminal.

Trin 1: Opret konfigurationen

Installér skill'en hvis du ikke allerede har gjort det:

/plugin marketplace add https://github.com/EmilMachine/skillhub
/plugin install dev-essentials

Kør derefter i dit projekt:

/devcontainer

Dette skriver en .devcontainer/-mappe ind i dit projekt med en devcontainer.json og en slank Dockerfile forudkonfigureret til Claude Code.

Trin 2: Start containeren

devcontainer up --workspace-folder .

Første kørsel bygger imaget - tager et minut eller to. Efterfølgende starter er hurtige.

Trin 3: Start Claude inde i containeren

devcontainer exec --workspace-folder . claude

Claude Code kører nu inde i containeren. Dine projektfiler er monteret og tilgængelige.

Stop

Stop (beholder containeren, hurtig genstart næste gang):

docker stop $(docker ps -q --filter "label=devcontainer.local_folder=$(pwd)")

Stop og fjern (rent udgangspunkt, genbygger ved næste up):

docker rm -f $(docker ps -aq --filter "label=devcontainer.local_folder=$(pwd)")

Valgfrit: shell-genveje

Tilføj til ~/.bashrc eller ~/.zshrc for nemheds skyld:

dev-bash() {
    devcontainer up --workspace-folder . && \
    devcontainer exec --workspace-folder . bash
}

dev-claude() {
    devcontainer up --workspace-folder . && \
    devcontainer exec --workspace-folder . claude
}

dev-stop() {
    docker ps -q --filter "label=devcontainer.local_folder=$(pwd)" | xargs -r docker stop
}

dev-down() {
    docker ps -aq --filter "label=devcontainer.local_folder=$(pwd)" | xargs -r docker rm -f
}

Så er dev-claude fra en vilkårlig projektmappe alt du behøver.

Hærdningsmuligheder

Hvis du arbejder med upålidelige projekter, er der sikrere alternativer til at bind-montere Claude-mappen.

Mulighed A - Skrivebeskyttet montering (enklest, men kan bryde ting)

Tilføj ,readonly til monteringsposterne i devcontainer.json:

"type=bind,source=${localEnv:HOME}/.claude.json,target=/home/devcontainer/.claude.json,readonly",
"type=bind,source=${localEnv:HOME}/.claude,target=/home/devcontainer/.claude,readonly"

Forbehold: Claude Code skriver til ~/.claude under kørsel (historik, indstillinger). Skrivebeskyttede monteringer vil sandsynligvis forårsage fejl eller stille miste tilstand.

Mulighed B - Kopiér ved opstart, ingen montering (sikreste)

Fjern ~/.claude-bind-monteringerne fra devcontainer.json og kopiér dem ind i stedet:

"postCreateCommand": "cp ~/.claude.json.host ~/.claude.json && cp -r ~/.claude.host ~/.claude"

Enklere med et shell-script - tilføj til postCreateCommand:

cp ${HOST_HOME}/.claude.json ~/.claude.json && cp -r ${HOST_HOME}/.claude ~/.claude

Containeren får et snapshot af din konfiguration og autentificering ved opstart. Korruption forbliver inde og forsvinder når du kører docker rm. Ulempe: skills installeret eller auth-tokens opdateret inde i containeren propagerer ikke tilbage - genbyg for at synkronisere igen.

Mulighed C - Kopiér ~/.claude/, montér .claude.json skrivebeskyttet (balanceret)

Montér kun auth-tokenen som skrivebeskyttet (så autentificering virker og ikke kan korrupteres), kopiér skills/config-mappen ind som et snapshot:

"mounts": [
  "type=bind,source=${localEnv:HOME}/.claude.json,target=/home/devcontainer/.claude.json,readonly"
],
"postCreateCommand": "cp -r ${localEnv:HOME}/.claude /home/devcontainer/.claude"

Auth er sikker. Skills er tilgængelige. Runtime-skrivninger går til containeren og dør med den.
