4. md3step

The md3step process: Research, Plan, Implement

This is the power-user pattern. Instead of one-shotting a complex task, you break it into three bounded steps - each producing a file the next step builds on. Two key benefits.

    1. It allows you to easily review, edit and refine plans.
    1. You can surface unknowns, and missing specification in your input.
Analogy - md3step

  • You don't walk into the doctor's office saying "I have stomach pain" and get put straight on the operating table.
  • First they do a checkup - gather information, understand the situation (/mdresearch).
  • Then they make a treatment plan - what to do and in what order (/mdplan).
  • Only then comes the treatment (/mdimplement).
  • The same logic applies here: jumping straight to implementation with a vague prompt is like skipping the checkup.

Install via skillhub:

/plugin marketplace add https://github.com/EmilMachine/skillhub
/plugin install md3step

Why md prefix?

The skills are named /mdresearch, /mdplan, /mdimplement, /mdupdate - not /research, /plan, etc. That's intentional. Words like plan, research, and implement are close to reserved or system-level keywords in various agents and tools now and in the future. The md prefix avoids silent collisions, and reference working with md files.

Why .md files?

  1. Main advantage is you can EDIT stuff. A lot of other flows it is hard to remove, change or add stuff in research or plans you want changed.
  2. Persist steps. When the 1_research.md file is done, you can close your computer, and come back next week and work on it. with a live session it is more difficult.
  3. Atomic steps. You can clear context between steps, and we can trust larger implementation pieces, because it is clean detailed input - ambiguity has been clarified.

Note there is some overhead. I normally use this for mid-large steps. Minor additions, debugging or tuning I do outside this framework.

The workflow

The process runs over four numbered files in a folder you choose:

0_context.md       ← you write this
1_research.md      ← /mdresearch produces this
2_plan.md          ← /mdplan produces this
3_changelog.md     ← /mdimplement produces this

You write 0_context.md. The three skills produce the rest. At each step you can read the output, answer open questions inline, and edit before moving forward - the agent waits for you.

Step 0: Write context

Create myprompts/my-feature/0_context.md and describe what you want to do, and relevant context needed to get it done. This is your input to the flow.

Step 1: Research

/mdresearch tasks/my-feature/0_context.md

The agent reads the codebase and writes 1_research.md in the same folder - current state, gaps, relevant file:line references. Open questions are surfaced at the top of the file. Read it, answer the questions inline, and run /mdupdate <path>/1_research.md to fold them into the main body before moving on. Ask for clarification or use /procon3 if you're unsure how to answer something.

Step 2: Plan

/mdplan tasks/my-feature/1_research.md

Produces 2_plan.md: numbered, atomic, testable steps. Each step has Actions, Files, and Verify sections. Open questions from research are carried forward; the agent tries to answer them from context before listing anything unresolved.

This is the step to edit. Add constraints, cut scope, reorder steps, answer open questions inline. The agent didn't decide the plan - you did, with its help. /mdupdate <path>/1_research.md

Step 0.5 (optional): update based on answers

If you added inline answers or edits to 1_research.md 2_plan.md:

/mdupdate tasks/my-feature/2_plan.md

/mdupdate folds your inline answers into the main body of the file, removes the resolved question markers, and raises any new questions that emerge from those answers. Skip it if you made no edits - it's not always needed. Without it the agent can usually work from your raw answers, but may miss follow-up questions and leave outdated text in the file body.

You can also use it deliberately: write your own question + answer pair and run /mdupdate to propagate a correction everywhere it matters.

Step 3: Implement

/mdimplement tasks/my-feature/2_plan.md

Executes each step sequentially, verifies after each, and writes 3_changelog.md with status per step, files changed (path:line), test results, and a Gotchas section if anything went sideways. No automatic git commits - review the diff yourself.

When not to use this

md3step is overhead for small tasks. Fixing a bug, renaming a function, adding a field to a type - do those in one shot. Use the process for anything that touches more than a couple of files, is complex or involves architectural choices.
