5. Run Claude Code in a sandbox

Claude Code can read files, write code, and run shell commands. That's its power — and its risk. If it makes a mistake or does something unexpected, you want that to happen inside a container, not on your machine.

A devcontainer runs your tools (Python, uv, Claude Code) inside Docker. Your code still lives on the host and is mounted in. If the container environment breaks, docker rm -f and rebuild.

What is and isn't protected

It's important to be honest here — a devcontainer is not a full sandbox for your files.

The following are bind-mounted from your host, meaning changes (and deletions) inside the container affect the real files:

Path inside container Host path
workspace folder your project directory
~/.claude.json ~/.claude.json
~/.claude/ ~/.claude/
~/.cache/uv ~/.cache/uv

A runaway rm -rf ~ inside the container would delete these on your host. Git is your safety net for code — commit often.

Note on ~/.claude in particular: we mount it so Claude Code is already logged in and has your skills and config available inside the container. The trade-off is that a compromised or malicious project could corrupt your Claude config — and that corruption would persist across every other project you open, since they all share the same ~/.claude from the host. It's a known risk. See hardening options at the end.

What is isolated:

  • Tool environment. Bad pip install, npm install -g, or apt installs stay inside the container and don't pollute your host.
  • Processes. Runaway processes, port conflicts, and background daemons are scoped to the container.
  • Clean slate on demand. Broken environment? docker rm -f and rebuild — your code and credentials are untouched because they live on the host.
  • Reproducible environment. Teammates get the same tools without "works on my machine."

The main protection is environment isolation, not file isolation.

Prerequisites

  • Docker installed and running
  • devcontainer-cli (pinned version to guard against supply-chain issues):
npm -g install @devcontainers/cli@0.87.0

Add to ~/.bashrc or ~/.zshrc:

export PATH="$HOME/node_modules/.bin:$PATH"

Source the file or open a new terminal.

Step 1: Scaffold the config

Install the skill if you haven't:

/plugin marketplace add https://github.com/EmilMachine/skillhub
/plugin install dev-essentials

Then run in your project:

/devcontainer

This writes a .devcontainer/ folder into your project with a devcontainer.json and a slim Dockerfile pre-configured for Claude Code.

Step 2: Start the container

devcontainer up --workspace-folder .

First run builds the image — takes a minute or two. Subsequent starts are fast.

Step 3: Launch Claude inside

devcontainer exec --workspace-folder . claude

Claude Code is now running inside the container. Your project files are mounted and available.

Stopping

Stop (keeps container, fast restart next time):

docker stop $(docker ps -q --filter "label=devcontainer.local_folder=$(pwd)")

Stop and remove (clean slate, rebuilds on next up):

docker rm -f $(docker ps -aq --filter "label=devcontainer.local_folder=$(pwd)")

Optional: shell shortcuts

Add to ~/.bashrc or ~/.zshrc for convenience:

dev-bash() {
    devcontainer up --workspace-folder . && \
    devcontainer exec --workspace-folder . bash
}

dev-claude() {
    devcontainer up --workspace-folder . && \
    devcontainer exec --workspace-folder . claude
}

dev-stop() {
    docker ps -q --filter "label=devcontainer.local_folder=$(pwd)" | xargs -r docker stop
}

dev-down() {
    docker ps -aq --filter "label=devcontainer.local_folder=$(pwd)" | xargs -r docker rm -f
}

Then dev-claude from any project folder is all you need.

Hardening options

If you're working with untrusted projects, there are safer alternatives to bind mount the Claude folder.

Option A — Read-only mount (simplest, but may break things)

Add ,readonly to the mount entries in devcontainer.json:

"type=bind,source=${localEnv:HOME}/.claude.json,target=/home/devcontainer/.claude.json,readonly",
"type=bind,source=${localEnv:HOME}/.claude,target=/home/devcontainer/.claude,readonly"

Caveat: Claude Code writes to ~/.claude at runtime (history, settings). Read-only mounts will likely cause errors or silently drop state.

Option B — Copy at startup, no mount (safest)

Remove the ~/.claude bind mounts from devcontainer.json and copy them in instead:

"postCreateCommand": "cp ~/.claude.json.host ~/.claude.json && cp -r ~/.claude.host ~/.claude"

Simpler with a shell script — add to postCreateCommand:

cp ${HOST_HOME}/.claude.json ~/.claude.json && cp -r ${HOST_HOME}/.claude ~/.claude

The container gets a snapshot of your config and auth at startup. Corruption stays inside and is gone when you docker rm. Downside: skills installed or auth tokens refreshed inside the container don't propagate back — rebuild to re-sync.

Option C — Copy ~/.claude/, mount .claude.json read-only (balanced)

Mount only the auth token as read-only (so authentication works and can't be corrupted), copy the skills/config directory in as a snapshot:

"mounts": [
  "type=bind,source=${localEnv:HOME}/.claude.json,target=/home/devcontainer/.claude.json,readonly"
],
"postCreateCommand": "cp -r ${localEnv:HOME}/.claude /home/devcontainer/.claude"

Auth is safe. Skills are available. Runtime writes go to the container and die with it.
