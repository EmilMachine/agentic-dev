5. Sandbox for coding agents

Why put a coding agent in a sandbox? So you don't have to worry about it deleting files, reading your secrets, or reaching out across your network. With that safety, you can let the agent do more on its own - even with --dangerously-skip-permissions.

This post covers three ways to build that boundary, each with a different blast radius. Not a strong preference but I recommend "nono" over "devcontainer" over "sbx / OpenSandbox".

nono is fast and uses global config profiles. Devcontainers and sbx need a per-project config file, but ship with tools pre-installed, easing org-wide rollout.

Devcontainers and sbx both use Docker. sbx adds a hypervisor on top - an extra layer protecting you if the agent escapes, at the cost of a slower startup.

Three ways to draw the boundary

Think of Claude Code as a dog living in your house:

  • nono - Dog inside the house, but most interior doors are locked; locked doors are as good as walls. Process-level sandbox (Landlock on Linux, Seatbelt on macOS) - same kernel, restricted syscalls.
  • devcontainer - Dog sealed inside a pod (a tipi) built within the house. Only what you put in the pod exists to the dog - but the pod shares the house's foundations, so a structural flaw can let it out. An OCI container - isolated environment, shared host kernel.
  • sbx - Dog in a separate building on the same plot, with its own foundations. Even if it breaks out, it's still outside - it was never in the house. A microVM - its own kernel.
See the dog metaphor drawn out

Security caveat: a sandbox only isolates what runs inside it. Anything Claude can still reach is attack surface - a mounted volume, an MCP endpoint, a live credential in an env var. All three tools shrink the blast radius, but none make an untrusted repo safe by default.

Quick pick:

Situation Pick
Windows 11, individual, minimal setup sbx
macOS / Linux, no MCP servers, low overhead nono
macOS / Linux, with MCP servers or hooks sbx or devcontainer
Team that wants the sandbox enforced in CI and local dev devcontainer
Untrusted repo / max isolation sbx (clone mode)

nono

nono is a process-level sandbox: Landlock on Linux, Seatbelt on macOS. No Docker, no VM - it hooks the kernel directly, so it starts almost instantly. It restricts which filesystem paths and network domains the wrapped process can touch; everything else is walled off.

The /nono skill scaffolds a .nono folder for you - no need to run it in every project.

Network policy: Claude Code only needs outbound access to claude.ai and api.anthropic.com - WebSearch also goes through them, but no package installs, no arbitrary curl. If a session needs real internet access, switch to the -web variant, which drops the network guardrail but keeps the filesystem/command restrictions. Default to the locked profile.

Install instructions

Step 1 - Scaffold

Install the skill if you haven't:

/plugin marketplace add https://github.com/EmilMachine/skillhub
/plugin install dev-essentials

Then run in your project:

/nono

This stamps a .nono/ folder into your project with profile templates. Pass -f to overwrite an existing .nono/. Full setup/usage reference: README_nono.md.

Step 2 - Install nono

# macOS
brew install nolabs-ai/tap/nono

# Linux
curl -fsSL https://nono.sh/install.sh | sh

Step 3 - Install the profile

Profiles live in ~/.config/nono/profiles/:

mkdir -p ~/.config/nono/profiles

# macOS
cp .nono/claude-mac.jsonc ~/.config/nono/profiles/claude-mac.jsonc

# Linux
cp .nono/claude-linux.jsonc ~/.config/nono/profiles/claude-linux.jsonc

Step 4 - Run

# macOS
nono run --profile claude-mac --allow-cwd -- claude --dangerously-skip-permissions

# Linux
nono run --profile claude-linux --allow-cwd -- claude --dangerously-skip-permissions

One-time login gotcha: the sandbox usually can't open the OAuth callback port. Log in outside nono first (plain claude, no wrapper), then relaunch sandboxed.

macOS note: login creds land in Keychain, which the sandbox can't read. The shell shortcut below extracts a token into ~/.claude/.credentials.json before each run - Linux creds already land there, so no extra step is needed.

Shell shortcuts

Add to ~/.bashrc / ~/.zshrc:

macOS:

nono-claude() {
  security find-generic-password -a "$USER" -s "Claude Code-credentials" -w \
    > ~/.claude/.credentials.json && chmod 600 ~/.claude/.credentials.json \
    && nono run --profile claude-mac --allow-cwd -- claude --dangerously-skip-permissions "$@"
}

Linux:

nono-claude() {
  nono run --profile claude-linux --allow-cwd -- claude --dangerously-skip-permissions "$@"
}

For a nonoweb-claude variant, copy the function and swap the profile to claude-mac-web / claude-linux-web. Reload (source ~/.zshrc), then just run nono-claude from any project.

What IS and ISN'T protected

✅ Covered ❌ Not covered
Claude's own file tools MCP servers started outside the process tree (SSE/HTTP)
Claude's own bash commands Hooks that call external APIs directly
Claude's own network calls

nono sandboxes the claude process; anything it delegates to outside that process tree runs unrestricted.

Config file reference - mounts, network, extra tools

Profiles are .jsonc files in ~/.config/nono/profiles/. For per-project tweaks without touching the shared profile, add ./.nono/local.jsonc that extends it - this one (A) adds a mounted folder, (B) allows a network domain, and (C) installs a tool group:

{
  "extends": "claude-mac",  // or "claude-linux"
  "filesystem": { "allow": ["$HOME/code/shared-lib"] },       // A
  "network": { "allow_domain": ["internal-api.example.com"] }, // B
  "groups": { "include": ["java_runtime"] }                    // C
}

Run it with:

nono run --profile ./.nono/local.jsonc --allow-cwd -- claude --dangerously-skip-permissions

Other runtime groups: node_runtime, python_runtime, go_runtime, rust_runtime, nix_runtime, homebrew, user_tools (a grab-bag for local CLIs). Run nono search <keyword> to find more.

devcontainer

A devcontainer runs your tools (Python, uv, Claude Code) inside Docker. Your code stays on the host and is mounted in. If the environment breaks, docker rm -f and rebuild.

Isolation model: a devcontainer shares the host kernel - a container (OCI), not a VM. Isolation is strong, but a kernel exploit could theoretically escape it - the trade-off against sbx below, which gives each session its own kernel.

Network policy: unlike nono, a devcontainer has no network restriction by default - WebSearch, WebFetch, and outbound calls all work out of the box. To lock it down, add iptables rules yourself; there's no built-in equivalent to nono's or sbx's allowlists.

What is and isn't protected

To be honest: a devcontainer is not a full sandbox for your files. The following are bind-mounted from your host, meaning changes (and deletions) inside the container hit the real files:

Path inside container Host path
workspace folder your project directory
~/.claude.json ~/.claude.json
~/.claude/ ~/.claude/
~/.cache/uv ~/.cache/uv

A runaway rm -rf ~ inside the container deletes these on your host. Git is your safety net - commit often.

Note on ~/.claude: it's mounted so Claude Code is already logged in with your skills and config available. Trade-off: a malicious project could corrupt that config, and the corruption persists across every other project sharing the same host ~/.claude. See hardening options at the end.

What is isolated: the tool environment (a bad pip install, npm install -g, or apt install stays in the container), and processes (runaway processes, port conflicts, background daemons stay scoped to it). Teammates also get the same reproducible toolset, no "works on my machine."

The main protection is environment isolation, not file isolation.

Install instructions

Prerequisites

  • Docker installed and running
  • devcontainer-cli, pinned to guard against supply-chain issues:
npm -g install @devcontainers/cli@0.87.0

Add export PATH="$HOME/node_modules/.bin:$PATH" to ~/.bashrc or ~/.zshrc, then source it or open a new terminal.

Step 1: Scaffold the config

Install the skill if you haven't:

/plugin marketplace add https://github.com/EmilMachine/skillhub
/plugin install dev-essentials

Then run in your project:

/devcontainer

This writes a .devcontainer/ folder with a devcontainer.json and a slim Dockerfile pre-configured for Claude Code.

Step 2: Start the container

devcontainer up --workspace-folder .

First run builds the image - takes a minute or two. Subsequent starts are fast.

Step 3: Launch Claude inside

devcontainer exec --workspace-folder . claude

Claude Code now runs inside the container, with your project files mounted and available.

Stopping, and shell shortcuts

Add these to ~/.bashrc or ~/.zshrc: dev-claude launches (steps 2+3 combined), dev-stop stops the container (keeps it for a fast restart), and dev-down stops and removes it (clean slate, rebuilds on next up):

# mac
dev-claude() {
    security find-generic-password -a "$USER" -s "Claude Code-credentials" -w \
    > ~/.claude/.credentials.json && chmod 600 ~/.claude/.credentials.json && \
    devcontainer up --workspace-folder . && \
    devcontainer exec --workspace-folder . claude
}

# linux
dev-claude() {
    devcontainer up --workspace-folder . && \
    devcontainer exec --workspace-folder . claude
}

dev-stop() {
    docker ps -q --filter "label=devcontainer.local_folder=$(pwd)" | xargs -r docker stop
}

dev-down() {
    docker ps -aq --filter "label=devcontainer.local_folder=$(pwd)" | xargs -r docker rm -f
}

Then dev-claude from any project folder is all you need.

VS Code

Install the Remote Development extension pack, open the project, then Cmd+Shift+P → Dev Containers: Reopen in Container. After config changes: Cmd+Shift+P → Dev Containers: Rebuild Container.

Config file reference - mounts, network, extra tools

All of this lives in .devcontainer/devcontainer.json (plus the Dockerfile next to it) that the /devcontainer skill scaffolded.

A) Mount more folders - add an entry to mounts, default to readonly (drop it only for a folder Claude genuinely needs to write to - same real-files caveat as the ~/.claude mount above):

"mounts": [
  "type=bind,source=${localEnv:HOME}/code/shared-lib,target=/workspaces/shared-lib,readonly"
]

Rebuild to pick it up: dev-down && dev-claude, or Rebuild Container in VS Code.

B) Allow more network traffic - nothing to "allow" by default. If you added iptables rules in postCreateCommand, add another the same way. Note iptables matches IPs, not domains - resolve first (dig +short example.com) or refresh with ipset if it changes. More fragile than nono's or sbx's allowlists; a sidecar proxy is the robust option.

C) Install/allow more tools - prefer a Devcontainer Feature (versioned, no Dockerfile edits):

"features": { "ghcr.io/devcontainers/features/java:1": {} }

Or edit the scaffolded Dockerfile directly (RUN apt-get install -y default-jdk). Either way, rebuild afterwards.

Hardening options

If you're working with untrusted projects, there are safer alternatives to bind-mounting the Claude folder. (Skip read-only mounts: Claude Code writes to ~/.claude at runtime - history, settings - so a read-only mount just breaks things.)

Option A - Copy at startup, no mount (safest): drop the ~/.claude bind mounts and copy them in via postCreateCommand instead:

cp ${HOST_HOME}/.claude.json ~/.claude.json && cp -r ${HOST_HOME}/.claude ~/.claude

The container gets a snapshot at startup; corruption stays inside and dies with docker rm. Downside: skills or tokens refreshed inside don't propagate back - rebuild to re-sync.

Option B - Copy ~/.claude/, mount .claude.json read-only (balanced): mount only the auth token read-only, and copy the skills/config directory in as a snapshot:

"mounts": [
  "type=bind,source=${localEnv:HOME}/.claude.json,target=/home/devcontainer/.claude.json,readonly"
],
"postCreateCommand": "cp -r ${localEnv:HOME}/.claude /home/devcontainer/.claude"

Auth is safe, skills are available, and runtime writes die with the container.

sbx (Docker Sandboxes)

sbx runs Claude Code inside a microVM - each sandbox gets its own Linux kernel, Docker daemon, filesystem, and network. Nothing inside can reach your host OS, files outside the project, or other processes. It's the strongest isolation of the three, and the natural pick on Windows 11 or for untrusted repos.

A regular docker run shares the host kernel - a container escape is possible. A microVM's kernel is its own, with nothing shared to escape to.

Install instructions

Install

Windows 11 - elevated PowerShell:

Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform -All   # one-time, requires reboot
winget install -h Docker.sbx
sbx login

macOS:

brew install docker/tap/sbx
sbx login

Linux: see distro-specific install steps, then sbx login.

Authenticate

API key (stored in the host secret store, injected by the proxy - never lives inside the VM):

sbx secret set anthropic

Claude subscription (OAuth): run /login inside Claude Code - the proxy forwards the flow to your host browser.

Run

sbx run claude ~/my-project

# Clone mode - sandbox gets a private copy; your working tree is untouched
sbx run --clone claude ~/my-project -- "Refactor the auth module"
Config file reference - mounts, network, extra tools

A) Mount more folders - pass extra paths as positional args; append :ro for read-only:

sbx run claude ~/my-project ~/shared-lib:ro

sbx picks the mount target, so this suits read-only reference material better than folders needed at a specific path.

B) Allow more network domains

sbx policy ls                                 # view current rules
sbx policy allow network registry.npmjs.org   # allow a specific domain
Preset Behaviour
Locked Down Blocked unless explicitly allowed
Balanced Default-deny + common dev sites - recommended
Open All outbound traffic allowed

C) Install/allow more tools - write a small kit YAML (a commands.install list of shell commands) and pass it with --kit:

sbx run --kit ./java-tools/ claude ~/my-project

--kit accepts a local path, an OCI registry reference, or a git+https://... URL. Community examples: docker/sbx-kits-contrib.

Known limitations

Limitation Workaround
~/.claude user config not visible inside VM Use project-level .claude/settings.json instead
SSH agent commit signing doesn't work inside Sign / rebase commits on the host after the session
MicroVM startup adds latency on cold start Keep sessions open; don't spin up and tear down repeatedly

⚠️ Enterprise callout: sbx pricing is a bit confusing. Per this source, sbx itself is free, including commercial use. What's paid is Docker AI Governance: org-wide policy pushes via the Admin Console, plus audit logging.

To self-host instead, OpenSandbox - Apache-2.0, with Alibaba involvement - is free, but you'd build that governance layer yourself.
