TL;DR — If you can't explain the code, you don't own it. New commands and code are learning opportunities - AI and colleagues can help.

C. Only Approve What You Can Explain

Claude writes 80 lines of authentication middleware. It looks plausible. Tests pass. You hit accept.

Three months later a colleague asks: "Why does this skip validation for internal routes?" You open the file. You have no idea. Neither does the model — it doesn't remember writing it.

The failure wasn't the code. It was the approval without understanding.

The real problem is amnesia

Undocumented, ununderstood agent code is opaque to everyone who comes after — including you. No one knows what tradeoff was made, what the model assumed, or what breaks if the context changes. A colleague can't ask the model. They'll ask you.

Put comments in — not what the code does, but why. If you can't write the why, you don't understand it yet.

Ask the model to explain the tradeoffs, not just the code. "What are the downsides of this approach?" surfaces assumptions it made but didn't mention. Then verify unfamiliar parts yourself — docs, source, examples. Thirty seconds of verification beats thirty minutes of debugging.

The test

Before approving anything non-trivial: could you walk a colleague through this in a ten-minute code review, without deferring to "the AI wrote it that way"?

That sentence tells no one anything useful. If you can name the key decision and say what breaks if assumption X changes, you understand it. If you're hoping no one asks, you don't.

This is actually an excellent opportunity to learn

Models are endlessly patient teachers. There is no shame in asking basic questions. Ask the model to explain a pattern you don't recognize, walk through an algorithm step by step, or justify why it chose one library over another. It won't judge you for not knowing. It won't get annoyed if you ask the same thing three different ways until it clicks.

Hard choices — a caching strategy, an auth design, an API boundary — are especially valuable to sit with. Ask the model to lay out the tradeoffs, then bring that to a colleague. "The model suggested X over Y because of Z — does that match how we think about it here?" That conversation builds shared understanding across the team in a way that solo acceptance never does.

The agents handle the writing. Understanding what they wrote — and owning it — is still yours, and it's the interesting part.

In Practice

  • If the agent asks to run a command or implement code you don't understand don't just approve. Ask to explain it. Explain like I am five (ELI5), using a fable what works for you.

Counter-arguments

"This kills the productivity gain." The gain was in writing, not thinking. You still need to understand what you're shipping — you just no longer have to write it first. Understanding a solution is faster than writing one.

"The AI is probably more correct than my review." For logic errors, maybe. For whether the code fits your system — your invariants, your security model, your business rules — no. The model solved the problem it was given. Only you know if that was the right problem.
