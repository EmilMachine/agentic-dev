TL;DR — LLMs are for fuzzy judgment. Parsing a date, sorting a list, validating an email — use code. Using an AI where a function works is like hiring a consultant to do arithmetic.

G. Don't Make an LLM Do What Another Tool Does Better

A fault reporting pipeline: workers report defective units by speaking into a handheld device. The system needs to log the unit ID from each report.

The first decision — transcribing speech to text — is exactly what a speech-to-text model is built for. Whisper, or any equivalent, handles accents and background noise. Right tool, right job.

The transcript comes out: "Unit 48821 is showing the wrong output, needs to be pulled."

The next step — extracting the unit ID — goes to an LLM. It's already in the pipeline. It feels natural. It works fine in testing.

But this is a regex task. Unit IDs follow a known pattern: \bU?\d{5}\b finds it every time. Deterministic, free, instant, testable. The LLM adds latency, cost, and the occasional surprising output for a problem that has an exact answer.

The engineer who reached for the LLM wasn't foolish — they were in a flow state where everything looked like an AI problem, because the step before it genuinely was one.

The hammer and the nail

Abraham Maslow — psychologist, best known for the hierarchy of needs — gave us the line: "If the only tool you have is a hammer, it is tempting to treat everything as if it were a nail."

LLMs are very impressive hammers. This makes the trap worse, not better. The more powerful the tool, the easier it is to reach for it by default.

The costs of over-using LLMs are concrete:

  • Latency: a function runs in microseconds; an LLM call takes hundreds of milliseconds to seconds
  • Cost: API calls cost money; functions don't
  • Reliability: functions are deterministic; LLMs occasionally return surprising results
  • Auditability: you can read a function's logic; you can't inspect why an LLM returned what it did
  • Testability: deterministic functions have deterministic tests; LLM outputs require sampling-based evaluation

None of these are hypothetical. They accumulate in any system that over-relies on LLMs for tasks code handles cleanly.

The right division

LLMs are genuinely superior at tasks involving fuzzy, context-dependent judgment:

  • Summarizing unstructured text
  • Classifying sentiment or intent
  • Writing prose, adapting tone
  • Reasoning about ambiguous requirements
  • Generating code from a description

Code (or traditional tools) is genuinely superior at everything that has a deterministic answer:

  • Parsing structured formats (dates, emails, JSON)
  • Sorting, filtering, aggregating
  • Arithmetic and logical operations
  • Schema validation
  • Pattern matching

The rule of thumb: if you could write a unit test with known inputs and expected outputs, and the function would pass it 100% of the time, use code. If the right answer depends on context a function can't capture, use the LLM.

A taxonomy of misuse

LLM as database query: "What is the current price of X?" The LLM guesses, may hallucinate, and can't know what "current" means. Use a lookup.

LLM as validator: "Is this a valid phone number?" Deterministic answer. Use a library.

LLM as classifier when a trained model exists: You need to categorize support tickets into 12 known buckets. An LLM works — but a small classifier fine-tuned on your own labeled data will be faster, cheaper, more consistent, and easier to evaluate. LLMs shine at open-ended classification where the categories shift or aren't known in advance. For stable, bounded label sets with training data available, a purpose-built model beats a general one.

LLM as router: "Does this belong to category A or B, where both are exactly defined in code?" Write an if-statement.

LLM as UUID generator: There is a function for this. In every language.

The exception

The fault reporting example also shows where the boundary gets genuinely complicated. A known unit ID pattern is a clean regex win — but if workers sometimes describe units by location or nickname ("the third press on line four") rather than ID, that mapping requires judgment a regex can't provide. There an LLM earns its place, with downstream code handling the resolved ID.

The combination — specialized model for audio, LLM for genuine ambiguity, code for structured extraction — is often optimal. The belief isn't "never use LLMs with structured data." It's "don't use LLMs for the part that has a deterministic solution."

References from other disciplines

Fred Brooks, The Mythical Man-Month (1975): Brooks' principle of using the right tool for each sub-task is foundational to software engineering. His broader point — that adding more of any one resource (people, in his case) doesn't fix structural problems — generalizes to tools. Using more AI doesn't fix a problem that needs a function.

Unix philosophy (Ken Thompson, Dennis Ritchie, 1970s): "Write programs that do one thing and do it well." The Unix design philosophy of composing small, specialized tools is the original answer to this problem. An LLM is one tool in a pipeline, not a replacement for the pipeline.

In practice

  • An LLM can both help research other methods and implement them. The difference between using an LLM to make a testable, scaleable component and using an LLM instead of the components is enormous.
    • I have seen problems where it would cost 40k EUR to run an LLM for a full classification task, and about 1 EUR to run a smaller and simpler ML models that performed much better than the LLM

Counter-arguments

1. "LLMs are getting faster and cheaper. Latency and cost concerns will disappear." Probably partly true over time. But deterministic functions will also get faster and cheaper — they're already nearly free. The gap may narrow; the principle doesn't change. Speed and cost aren't the only reasons to prefer code: auditability, testability, and determinism matter independently.

2. "Using LLMs for everything keeps the architecture simpler — one component instead of many." Simpler to build, harder to maintain, debug, and scale. "One component" sounds elegant until you're trying to explain to a client why the answer to "what is 2+2?" occasionally returns "approximately 4". Complexity hidden inside an LLM is not eliminated; it's made invisible, which is worse.

3. "Sometimes I don't know in advance which tasks are deterministic." True — and the answer is: default to code when in doubt, and refactor toward LLM when you discover the task genuinely needs fuzzy reasoning. The reverse (default to LLM, discover it was overkill) is a more expensive mistake to undo.
