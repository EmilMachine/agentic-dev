TL;DR — Big-bang delivery fails. Small steps surface surprises early, when fixing them is cheap. AI makes iteration nearly free. Prioritize testing — like a carpenter jumping on a new floor to make sure the foundations hold before moving on. Jump on your code.

E. Build and Validate in Small Steps

Bent Flyvbjerg's research across thousands of large projects shows roughly 92% come in over budget, over time, or both. The root cause is almost never incompetence. It's surprises discovered too late — assumptions baked in early that nobody checked until the cost of unwinding them was enormous.

The solution isn't better planning. It's shorter loops with validation at each one.

"No plan survives first contact with the enemy." — Helmuth von Moltke the Elder (paraphrased)

What goes wrong in big steps

When you hand an AI a large, loosely specified task and come back an hour later, the model made assumptions you didn't catch early enough. The bigger the task, the more assumptions, the more expensive to reverse. Does your data actually look like you thought? Does the API return what the docs say? Is the architecture sound at small scale?

Small steps answer these when the answer is still cheap to act on.

Jump on your code

A carpenter laying a new subfloor doesn't immediately start on the cabinets. He jumps on the floor first — literally puts weight on it, walks the edges, bounces a little. If it flexes wrong or a board shifts, he fixes it before anything is built on top of it. Putting cabinets on a bad subfloor means ripping out the cabinets to fix the floor.

Tests verify logic. Jumping on the floor is different — it's manual, physical, deliberate load-testing before the next layer goes on.

Do the same with code. After each small step: run it, click through it, feed it bad input, hit the edge case. Make sure it holds the weight before you build on top of it. You'll catch things tests miss — wrong UX flow, a third-party API that behaves differently than its docs, a performance cliff that only appears with real data.

AI makes small steps cheap

Before agents, small steps had a friction cost — you had to write each increment yourself. That nudged people toward larger chunks.

That friction is mostly gone. Generating a 50-line implementation is as fast as generating a 500-line one. The only cost of going smaller is discipline.

Scope each task to one coherent unit of behavior. Validate it — including manually. Then go to the next.

Too big: "Refactor the entire auth module to use JWTs, update the schema, and migrate existing sessions."

About right: "Replace session token generation in @src/auth/session.ts with a JWT. Don't touch the database yet."

In practice

References from other disciplines

Bent Flyvbjerg, How Big Things Get Done (2022): Flyvbjerg's data from thousands of megaprojects shows that the projects that succeed plan modularly — breaking large efforts into repeated, validated patterns — rather than attempting end-to-end execution in one go. The principle applies at the task level, not just the project level.

Toyota Production System — jidoka and andon cord: Toyota's manufacturing philosophy includes stopping the line the moment a defect is detected, rather than continuing and fixing it downstream. Defects caught at source cost a fraction of defects discovered at delivery.

Kent Beck, Extreme Programming (1999): The XP practice of short release cycles and test-first development is the software formalization of the same idea. Validate constantly; don't save validation for the end.

Counter-arguments

"Some tasks can't be decomposed." Fewer than you think. If you genuinely can't decompose something, that's a signal the task isn't well understood yet — which is itself a reason to start smaller.

"Small steps create overhead." Bounded overhead. Debugging a 500-line diff you didn't write, untangling conflicting assumptions, explaining to a client why the feature isn't what shipped — that overhead is unbounded.

"I trust the AI to get large tasks right." Even correct code can be wrong for your context and undocumented invariants. Validation checks context, which only you have. Of course automated tests can help agents in the loop, but edgecases always exists. Make it feasible and easy to "jump on code" and find the blindspot errors as well.
