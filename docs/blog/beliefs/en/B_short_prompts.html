B. A Prompt Should Be As Short As Possible (But Not Shorter)

You might have heard the alleged Einstein quote "Everything should be made as simple as possible, but not simpler." He did not write prompts for LLMs but very elegant papers - that changed how we all think about space and time. Let us be real, we have a far simpler job - giving a good input to an input-output machine.

We have growing context windows, and I hear a lot of people praising that like it will solve everything. I strongly believe we should still do our best to keep context minimal.

It is important to be precise and brief because, not doing so is wasteful and often counterproductive. More input does not give better output. Quality over quantity.

It is even worse for AI input and output machines.

Why? A key invention in AI (LLMs) is something called attention - basically each word affects each other - so N x N scaling - if my input prompt is 10x the length it is both 100x more memory and compute. People have made some tricks to do linear memory but compute remains quadratic.

To put a picture to it. You are on an old-school steam locomotive. The boiler is burning 100 times as hot as needed, because you shovelled 10x shit into the burner.

So what is a brief and precise way to express that?

  • Terse

That is my favourite word working with AI (LLMs). I want a terse report, terse skills, reduce the text to 50% length. Make it terse.

Quality

Let us look at the quality of output based on input. How can the input cause fails:

  • A) Info is missing
  • B) Info is wrong
  • C) Info is hard to find (diluted)

Terse - is directly addressing C) - important stuff has less risk to disappear or not be used, if we removed the unimportant stuff.

However shorter text also make it easier to spot A) and B) in review.

The "but not shorter" part

We need enough input to actually solve the task. Brevity without clarity is just vague. "Fix it" is short. It's also useless.

The minimum viable prompt has three things:

  • What you want done
  • The context needed
  • Any constraints that would change the answer.

A concrete example

Long version (54 words):

"Please analyze the following code and look for any bugs or issues that might cause problems in production. Make sure to check for edge cases, error handling, and potential security issues. Please be thorough and professional in your analysis and provide clear explanations."

Short version (8 words):

"Find bugs and security issues in @src/auth.ts, Write a terse report to @myreports/security_auth.md"

The short version produces a better result. The long version tells the model how to do its job. The model already knows how to do its job.

Other inspiration

William Strunk Jr., The Elements of Style (1918): "Omit needless words." Strunk wrote this for prose writers, but it applies to prompts character-by-character. Every needless word in a prompt is a needless word.

Information theory (Shannon, 1948): A message's value is proportional to how much it reduces uncertainty. Words that don't reduce uncertainty add noise, not signal.

Counter-arguments

1. "Complex tasks need complex prompts." Sometimes true. Multi-step tasks may genuinely need structure. But even then, the structure should be minimal — task decomposition beats one giant paragraph. The belief isn't "never write long prompts", it's "don't write long prompts by default".

2. "More context helps the model produce better output." Up to a point. Relevant context helps. Irrelevant context — including over-specification — has been shown to degrade model performance. The model treats your constraints as authoritative, even when they conflict with what you actually want.

3. "Short prompts leave too much room for misinterpretation." If the output surprises you, you can iterate. One short prompt + one correction round is usually faster and clearer than getting the first prompt right through brute-force specification. Treat the first output as a draft, not a final answer.

4. "My team needs detailed prompts for consistency." Team consistency is a real concern. But the solution is documented prompt templates or shared CLAUDE.md context, not adding words to every individual prompt. Document the context once; reference it everywhere. (See Belief D.)
